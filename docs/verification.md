## v0.8 ↔ v1.0 の状態形式互換性

**結論：元のv0.8と今回のv1.0候補は、状態の読取・保存形式が両方向で互換です。** ただし、実機の状態健全性や外部処理の成否、あらゆる運用条件での復旧成功を保証するものではありません。

方法：

1. 元のv0.8ローカル `aa519da` の `riri/state.py` をバイト単位で保存し、原本のGit blob SHAとSHA-256を照合。
2. その原本を現行StateStoreとは別のモジュールとして実行。依存する現行 `riri/noa.py`・`riri/errors.py` と現行 `riri/state.py` も、元のv0.8とSHA-256が同じでなければ試験を失敗させる。
3. 架空の状態を、v0.8→v1.0とv1.0→v0.8、本番/練習の4組合せで保存・読取・再保存。全フィールドと保存バイトの一致を確認。
4. 6回の交互読み書きでも、重複防止、既読報告、再送許可・消費、sending/held、Noaの全8状態・10試行の履歴、失敗episode、古い受付区間、未確定ログバッチを保持。
5. 11種類の不正入力を両readerで拒否し、22ケースで原本state・ログを書き換えないことを確認。
6. 過去のGitオブジェクトやネットワークがないコピーでも互換性7試験が成功。GitHubから新しく受け取ったソースだけで再実行できる。

[詳細な検証記録](state-compatibility.json) ／ [原本の出典・ハッシュ](../tests/fixtures/v08_state/manifest.json)

この試験は永続化・スキーマを対象とします。架空レコードを巡回の全業務経路で実行した証明ではありません。依存ソースのハッシュが将来変わった場合、この試験が失敗するのは再検証が必要という意味です。ハッシュを書き換えるだけで互換としません。

### バックアップを戻すこととは別

両方向に読めるため、復旧時は **v0.8のコードへ戻し、最新state/logsを維持する** のが原則です。更新後に送信・起動・試行があったのに更新前stateへ戻すと、事実を忘れて二重実行につながります。自動復元・初期化・キー削除・ログ削除を許可するものではありません。

実stateが欠損・破損していればSTOP維持。`StateStore.load`はファイル欠損を初期状態として返すため、`--status`の0件表示だけを健全性の証拠にしないよう手順へ明記しました。実state自体は今回取得していません。

## Noaと復旧手順の注意点

- STOPは送信済み通信・開始済みNoaセッションを取り消せません。設定をfalseに変えても、実行中プロセスは読込済み設定を保持します。
- STOP・自然終了後にlaunchdを解除。途中でbootoutして不明結果を作らないよう、先に実行終了を確認します。
- `--status`は正常時ローカル読取。エラー時は動作ログへ追記し得ます。通常の `--dry-run`は実Slack・Notion読取を行い、練習state・ログを更新します。STOPのままの即終了を接続成功とは数えません。
- launchd解除下の単発dry-runでSTOPを一時解除する場合は、本人の実接続確認承認を必要とし、直後にSTOPを復帰・存在確認。RunAtLoadによる再開と手動巡回を重ねません。
- NoaのON前はOFFの本番観測を確認。STOP・status・practiceだけでは本番のOFF観測になりません。
- 有効化直後の境界作成を確認してから、人から1件だけ無害な新規投稿で試験。元のtsと実セッション履歴を照合し、結果不明時は再投稿しません。
- りり・bot・STOP・練習で起動しないことはオフライン確認済み。実機での追加実証は今回未実施で、操作ごとの本人承認が必要です。
