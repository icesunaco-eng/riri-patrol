## 固定プログラムが行うこと

- STOP、二重起動ロック、4分以内の終了、Slackボットの本人確認を先に行います。
- 未着手の依頼を古い順に処理します。1回の指示は最大1件、指示・報告・通知を合わせて最大4件です。
- みにへの伝言、りり自身宛ての除外、5人の完了報告、全宛先完了時の状態更新を扱います。
- 書き方が不正な完了報告は、その報告だけを飛ばして「たかむねりりあいす」へ形式確認を1回通知します。同じページ・ブロック・本文には繰り返し通知しません。ほかの依頼・報告は続行し、不正な報告から関連する依頼を推測して完了・再送にはしません。ID不明時はその報告ページを根拠にした自動完了のみを待機し、通知にも「この報告が直るか消えるまで、○○のページの報告での自動完了は待ちます」と明記します。
- 出来事をローカルに保持し、3時間ごとにNotionの指定9列表へ新しい順で追記します。
- LLM接続が確認できた場合も、Qwen3.6に任せるのは末尾の挨拶の調整だけです。現在の配布見本ではLLMは無効です。依頼内容・宛先・手順・期限は固定し、ツールは渡しません。不正な出力や接続失敗時は固定文面に戻します。
- ボットトークンが本人ID `U0C5V11S37X` を名乗る場合は拒否します。別途承認された本人トークンだけ、上記の固定報告先・限定kindに使用します。

## 設定と練習モード

秘密の値をREADME・チャット・GitHubへ書かないでください。`.env.example` は秘密と本人確認IDが空の見本です。既存の本物の.envは対象Macだけで保全し、見本で上書きしません。新しい設定の追加や配備は別途承認後です。

すべての設定を.envだけから読みます。ターミナルの環境変数による本番化・トークンの差し替えはできません。末尾の ` # メモ` はコメントとして扱います。引用符の中の # と、空白なしのURL断片 # は値の一部です。変数・コマンド・バックスラッシュの展開はしません。不正な引用符は値を出さず停止します。`RIRI_MODE=live` と本人が.envに書いたときだけ本番です。未設定・誤記は練習です。本番の見回り開始時は `本番（.envより）` と記録します。

`EXPECTED_SLACK_BOT_ID`・`EXPECTED_SLACK_USER_ID`・`ICE_MENTION_USER_ID` が未設定・空欄なら、練習でも停止します。コード内の固定IDへは戻しません。`--status` は本人確認を実行しないためICE_MENTION_USER_IDの不備を検出する検査にはなりません。本人が実接続確認を許可した段階で、対象Pythonによる `--dry-run` の `status=ok` を確認します（STOPで終了したstoppedを合格にしません）。今回この実接続操作は未実施です。期待IDが空欄でも停止記録を保持できるよう、設定読込と本人確認を分離しています。Slack認証・投稿・依頼処理は進めません。

```bash
# 配備承認後の操作説明。読み取りは行いますが、Slack・Notionへは書きません。
python3 patrol.py --dry-run --verbose

# 状態の概要だけ。通信・状態変更なし（.envの設定は必要）。
```

練習と本番は同じ書き込み検証を通り、練習では最後の外部書き込みだけ止めます。Slack文面・チャンネルID、Notionの書き込み直前の再読込・本文・編集版・状態遷移、ログ表の列名を確認します。練習と本番の状態ファイルは別です。

練習では「対応中にしたつもり」「完了にしたつもり」の状態を練習用状態ファイルへ保存します。Notionの実本文は未着手のままでも、拾う→指示の練習→全員の報告→完了の練習まで通ります。実本文・編集版・ブロックは毎回検証し、遷移判定だけに練習状態を使います。本番ではこの仮想状態を使えません。デモはNotion側の架空状態を手で変えずに最後まで確認します。

## STOP

プロジェクト内の `STOP` ファイルで止まります。`STOP_FILE` で別の場所も指定できます。停止中は状態を変更せず動作ログに1行だけ残します。実行途中も各通信の直前に確認します。すでに送った通信を取り消すことはできません。Slackの通信前ガードでSTOPまたは時間切れになり、未送信と確認できる場合だけqueuedへ戻します。STOPならその回を終了します。送信前と分かる単発の時間切れは、動作ログへ1行残してstatus=deadlineで終了し、余計なエラー通知・復旧通知を増やしません。連続する時間切れは状態へ記録し、3回続くか、「最後の完走」と「今回の最初の期限切れ」の遅い方から30分以上たった場合に、一度だけ知らせる通知を予約します。期限を超えて送信することはせず、次の実行の本人確認後、重い読取より先に通知します。本体の完走はNoa処理より先に保存します。完走確認後の復旧通知も次の安全な実行で送ります。本体のエラーと期限切れが同時に解消したときは1通へまとめます。Noaの認証・設定の失敗記録だけでは本体の復旧を妨げませんが、結果不明の保留は引き続き確認が必要です。通知の送信結果が不明なら再送せず保留します。Notionの状態更新・ログ追記も同じで、未送信の待機データを保持します。送信後の結果不明は従来どおり保留です。時間切れも実行上限を延長せず終了します。この未送信分はpostsに数えません。postsは実際の送信試行数（練習の送信相当を含む）で、通信した後のエラーや結果不明は安全上、上限に数えます。通信が始まったか不明なら保留を維持します。

## Slack投稿が保留になったとき

投稿には `rp:英数字` の照合用の印が1行付きます。履歴はHTMLエスケープを戻し、同じボット・同じ印の行・有効なtsを確認します。履歴を最後まで読めない場合や一致がない場合は自動再投稿せず保留にします。送信直後のtsは状態ファイルへ保存します。

一度heldになった依頼は、後から履歴に現れても自動解除しません。たかむねが履歴を確認して、次のいずれかを実行します。

```bash
# 実際に出ていることを確認済み。再投稿しない。
python3 patrol.py --resolve '依頼ID' posted

# 実際に出ていないことを確認済み。次の見回りで一度だけ投稿を許可。
python3 patrol.py --resolve '依頼ID' not_posted
```

この操作は通常の見回りと同じロックを取り、Slack投稿結果がheldの依頼だけを変更し、変更をローカルログへ残します。通信はしません。not_postedは「一度だけ許可」の印を付けます。次回の送信意図を保存するときに許可を消費し、成功時や再保留時にも印を残しません。繰り返し投稿しません。元のNotion状態が対応中でも許可されますが、本文変更・完了・削除等は再検証して止めます。再び結果不明なら再度heldです。保留の回数ごとに別の通知を1回だけ用意するので、2度目の保留も見落とさないようにします。通知も1回4件の上限内です。

postedによる手動確認では、確認できていないtsを作りません。練習状態を解決する場合は `--dry-run` も付けてください。STOP中はresolveもしません。状態ファイルを削除してやり直すと重複投稿の危険があるため、削除しないでください。

### 指示以外の保留も手動確認できます

まず `python3 patrol.py --status` の `held` 一覧で種類・ID・選べる結果を確認します。本文や秘密は表示しません。以下はすべて同じロックを取り、ローカル状態と監査だけを変更します。外部通信やその場での再送はしません。練習状態なら `--dry-run` を付けます。

```bash
# 指示（従来の2引数でも同じ）
python3 patrol.py --resolve instruction '依頼ID' posted
python3 patrol.py --resolve instruction '依頼ID' not_posted

# 指示以外のSlack通知・まとめ報告。履歴で結果を確認して選ぶ。
python3 patrol.py --resolve notice '一覧のID' posted
# 出ていないと確認済みなら、次の回に一度だけ再送。
python3 patrol.py --resolve notice '一覧のID' not_posted
python3 patrol.py --resolve notice '一覧のID' cancel

# Notionの本文・状態と監査ログを照合し、元の依頼内容を復元して確認した場合。
# 保留の知らせに、この依頼で使えるコマンドが書いてある（続きに戻せない保留では cancel だけ）。
# まむ・みき・みにの受け口に渡した依頼は、checked で受け口の分として続く（報告で完了まで進む）。出し直さない。
python3 patrol.py --resolve notion '依頼ID' checked
# この依頼の続きを取りやめる場合。
python3 patrol.py --resolve notion '依頼ID' cancel

# 依頼の「状態」の行を書き換えられずに保留した依頼（種類 status）。
# 新しい依頼IDで書き直した場合（始めの保留・完了の保留のどちらも）。
python3 patrol.py --resolve status '依頼ID' cancel
# 報告がそろったあとの保留で、状態の行を手で「完了」にした場合（完了の保留だけ）。
python3 patrol.py --resolve status '依頼ID' done
# まむ・みき・みにの受け口に渡したあとの保留で、状態の行を手で「対応中」にした場合（受け渡しの保留だけ）。
# 新しい依頼IDで出し直すと同じ作業がもう1回動くので、出し直さない。
python3 patrol.py --resolve status '依頼ID' checked

# Notionログ表で、当該バッチの全出来事IDが書かれたことを確認した場合。
python3 patrol.py --resolve log '一覧のバッチID' written
# 書かれていない分があると確認した場合。一部だけ反映された場合もこちら。
python3 patrol.py --resolve log '一覧のバッチID' not_written
```

- noticeのpostedは、その通知の既読印・通知時刻も通常成功と同様に更新します。not_postedは次回一度だけ再送し、成功するまでは報告の既読印や成功記録を進めません。cancelは投稿したと偽らず取りやめ、その報告の同じ版を繰り返し送らない印を付けます。報告の「完了報告を見つけた」記録は「取消のためSlackへ送らなかった」と明記して残し、通常のNotionログまとめ対象にします。別の新しい報告・エラー通知まで永久に止めません。
- notionのcheckedは、別の依頼内容への変更を承認する機能ではありません。元のブロックと元の依頼本文へ戻したことを確認してから使います。次回も元の本文・ブロック・状態を再検証してから処理を再開し、既存の指示はそれまでblockedです。内容自体を変更したい場合はcancelして新しい依頼IDを使ってください。
- statusは、受け付けた依頼の「状態」の行を Notion で書き換えられなかったときの保留です（その依頼だけ止まり、ほかの依頼は続きます。メンションなど文字以外の部分がある依頼もこうなります）。保留の知らせに、使うコマンドがそのまま書いてあります。始めの保留は cancel だけ、受け口に渡したあとの保留は checked か cancel、報告がそろったあとの保留は done か cancel を選べます。
- logのwrittenは全IDが反映済みと確認できた場合だけです。不明なら解除せず確認を続けます。一部反映ならnot_writtenとし、次回に表全体を読み直して反映済みIDを除き、残りだけ追記します。未反映の出来事を捨てません。
- 保留の取消・解除は履歴を残します。保留中は誤って「直りました」と知らせません。容量通知も手動解除後は再判定できます。

### 安全でない文面があった場合

今回の投稿に使う依頼・報告だけをチェックします。古い完了依頼や、投稿に使わない補足欄の文字で全体を止めません。不適切な文面はその1件だけheldとして安全な固定通知を出し、他の依頼・報告を続けます。通知には安全な形式の依頼IDと報告した子を入れ、危険な原文は引用しません。

`held` 一覧のrequest/reportに `source_edit_required` と出る場合は、元の本文を直します。この種類はresolveで無条件に送信許可できません。修正された別の本文を次回改めてチェックします。新しい報告が保留のとき、同じ依頼の古い「完了」を代わりに使って完了扱いにはしません。

送信前の安全チェックで止めた通知はunsafe_contentと表示し、選べるのはcancelだけです。送信していない通知をpostedにしたり、不適切な文面をnot_postedで再送したりできません。

安全チェックで止めた指示は、送信前だったと確認できる場合だけ、修正後の本文を再検証・再作成して処理します。Notion側が対応中でも一覧から消えたままにはしません。不完全な修正なら保留を表示し続け、りり自身だけへの修正では古い指示を取消して除外通知だけを出します。元の不適切な依頼がページから削除された場合は保留を外し、source_removedとして記録を残します。消した依頼IDが後で再登場しても自動復活しません。未完了の同じIDが再登場した場合は「取りさげた依頼IDです、新しいIDで書いてください」と1回だけ安全な通知を用意します。ID欄を一時的に空にした後で直した場合も同じです。通知は通常の投稿上限内で送り、結果不明なら再送せず保留します。必要な新しい依頼には新しいIDを使ってください。

- 入れる（段1）：りりのフォルダの `.env` に `MINI_TRANSPORT=local` と `MINI_STAGE=1`。本番モード（`RIRI_MODE=live`）で STOP がなく、`MINI_*` の設定に誤りがないときだけ動く。前に済ませること：
  - 専用ホーム（`MINI_CODEX_HOME`、決めていなければ `~/.codex-riri`）を配備の形にする。`config.toml` に書けるのは `model`・`model_reasoning_effort`・`project_doc_max_bytes`・`[features]`・`[agents]` だけで、`model`（`MINI_VERIFIED_MODEL`、既定 gpt-6.2-sol）と `project_doc_max_bytes = 0` は必ず書き、`[features]`・`[agents]` の値は false だけ。`AGENTS.md` を置く。ログインは、たかむねが専用ホームを指定して `CODEX_HOME=~/.codex-riri codex login` で済ませ、`CODEX_HOME=~/.codex-riri codex login status` で確かめる（`CODEX_HOME` を付け忘れると本番の `~/.codex` にログインしてしまい、受け口は 401 で「できなかった（ログイン切れか認証の誤り）」が続く。`MINI_CODEX_HOME` を決めたときはその場所にする）。形が違えば `mini-home` の知らせが出て起こさない（確かめる中身は `riri/mini_lane.py` の `home_problems`）
  - Codex CLI と macOS の版が `MINI_VERIFIED_CODEX`・`MINI_VERIFIED_MACOS`（既定 0.169.0・27.2.1）と同じこと。違えば起こさず `mini-version` の知らせが出る。版を上げるときは、のあに頼む：専用ホームをサンドボックスの外から1回起動して初期化し、境界の試験（`python3 -B -m unittest tests.test_mini_profile`、macOS の本物の sandbox-exec）と、本物の Codex の通し（ふつう・実行中の STOP。台本はのあの手元）をやり直してから設定を直す
  - 設計の版ハッシュ：りりのフォルダで `python3 -m riri.mini_lane design-hash` を流し（りりの Notion の接続で設計 v1.0 のページを読み、設計の 8 の Y7 の取り方で計算する）、出た `MINI_DESIGN_HASH=…` の行を `.env` に書く。ないと受け口は起こさない（設定の誤りとして止まる）。run ごとに起動の記録と完了報告の証拠欄（`版ハッシュ=`）に残る。設計に書き足したら計算し直して書き換える（受け口を止めてから）
  - 段2（`MINI_STAGE=2`、案件フォルダに書ける）は、段1を確かめてから別に決める。段2でも、みにの `AGENTS.md`（`~/みに/AGENTS.md` と各案件・独立監視の `AGENTS.md`）は書けない
- 止める：`MINI_TRANSPORT=off` か `MINI_STAGE=0` にする。止めても、もう起こした run は見張り役が最後まで見て、報告も届ける。まだ起こしていない予約は起こさない（みにだけの依頼は今までどおりの案内になり、ほかの子と一緒の依頼のみにの分は `mini-off` で知らせる）。STOP はりり全体を止める：動いている run も止め（報告は「一部完了（STOPで中断）」）、報告は STOP を外したあとの巡回で届く
- run ごとに残るもの：りりのフォルダの `state/mini`（run の記録・標準出力と標準エラー・見張り役のログ）、run のフォルダ（`MINI_RUN_DIR`、決めていなければ `~/.riri-mini-runs`。写し・作業用のフォルダ）、専用ホームの `sessions`（会話の記録）。どれも自動では消さない。`state/mini` は「ログの容量通知」に入るが、run のフォルダと会話の記録は入らないので、たまに大きさを見る（2026-11-25 の小さな依頼で、run のフォルダは1件 約80KB、会話の記録は1件 約170KB）。整理するかはたかむねが決める。`state/mini/runs` の記録は、整理のために消さない。同じ受付をもう一度起こさないための記録で、消すと同じ依頼をもう一度起こしたり、会話前に終わった依頼で巡回が止まったりする（読めない記録の扱いは下の表の `mini-broken`）
- コードをこの受け口の前の版に戻す：先に受け口を止めて、次を確かめてから戻す。前の版は `state/mini` を読まないので、残っていると報告が届かないままになったり、巡回が止まったりする。`state/mini` は消さずに残す
  - `state/mini/runs` に、起動の印（`launch_mark`）があって終了の証拠（`end_evidence`）がない run と、報告が `pending`・`unknown` の run がない。`--status` には出ないので、りりのフォルダで次を流して見る（読むだけ。1行に run・依頼ID・状態・起動の印・終了の証拠・報告・受け渡し。受け渡しが skipped で「会話が始まらなかった」の run の依頼が、下の「会話が始まる前に終わった」依頼）

    ```bash
    python3 -c "import glob,json; [print(p.split('/')[-1][:-5], r.get('request_id'), r.get('state'), '印あり' if r.get('launch_mark') else '印なし', '終了あり' if r.get('end_evidence') else '終了なし', '報告:' + (r.get('report_state') or '-'), '受け渡し:' + (r.get('handoff_state') or '-'), r.get('handoff_reason') or '') for p in sorted(glob.glob('state/mini/runs/*.json')) for r in [json.load(open(p))]]"
    ```

  - 会話が始まる前に終わった、みにだけの依頼（「未着手」のまま、みにの「できなかった」の報告があるもの）がない。前の版の巡回は、これを「同じIDの過去報告」として毎回エラーで止まるので、戻す前に手で「完了」にするか消す

## みにの受け口の知らせと保留（MINI_TRANSPORT=local）

みにの受け口の保留は、その run の記録（りりのフォルダの `state/mini/runs/<run>.json`）に残ります。`--status` の `held` には出ません。どれも、その依頼（またはみにの起動）だけを止め、ほかの依頼と「直りました」は止めません。知らせには、次にすることが書いてあります。

| 知らせ（outbox のキー） | 何が起きたか | すること |
| --- | --- | --- |
| `mini-hold:<run>` | 見張り役がいないのに終了の証拠がない、または run の仲間が残っている | 知らせには子の PID と、その子が「動いている」「もういない」「動いているか分からない」が出る（番号と始まった時刻で見ている）。子が動いているなら止める。子のプロセスが終わったことを確かめてから、りりのフォルダで `python3 -m riri.mini_lane record-end <run> --by たかむね`。記録するまで、次のみにも起こさない。record-end が「run の仲間がまだ残っている（PID …）」と言ったら、その PID を `ps -o pid,lstart,command -p <PID>` で確かめる。run のもの（run が動いていたころに始まった・みにの作業のコマンド）なら止めてからやり直す。run が終わったあとに始まった関係ないプロセスに見えるとき（番号の使い回しのまれな場合）は、止めずにのあに相談する。見張り役は、子孫を「生まれたときの親の番号」でたどる。たどれないもの（親が見られずに終わったもの）は run のものかもしれないとして数えるが、止めない。record-end はそれを「run のものか分からないもの」として別に出す。そこには run の最中や、run のあと record-end までに始まった関係ないプロセスも入りうるので、時刻だけで決めず、run のフォルダの中で動いているか（`lsof -a -d cwd -p <PID>`）とコマンドで確かめ、run のものと分かったときだけ止める。分からなければ止めずにのあに相談する。子が run のサンドボックスにいると確かめられた run では、そのサンドボックスにいないものは run のものではない（見張り役が数えない）。子がどれかのサンドボックスにいた run では、どのサンドボックスにもいないものは run のものではない。関係ないと確かめたプロセスで record-end が通らないときは、そのプロセスが終わるのを待つか、のあに相談する。保留の理由が「子が最後に起こしたプロセスをたどれず」「run のサンドボックスに聞けなくなり」「子が run のサンドボックスにいると確かめられず」のとき（理由の後ろに添えられたときも同じ）は、record-end の確かめが弱い（見張り役がたどれなかった・サンドボックスに聞けない）。record-end の前に、run のフォルダの中で動いているプロセスがないか（`lsof +D <run のフォルダ>`）も手で確かめる |
| `mini-broken:…` | 読めない run の記録がある | `state/mini/runs` のそのファイルを確かめて直すか、別の場所へ移す。次の巡回からまた起こす |
| `mini-held:<run>`・`mini-x4:<run>` | 起こす直前の確認で保留した／資料が2回続けて変わった | その予約はもう起こさない。何を直すか（依頼・資料・りりのフォルダや run の置き場）は知らせに書いてある。みにだけの依頼は、直したら（資料が落ち着いたら）新しい依頼IDで出し直す（元の依頼はそのままでよい）。ほかの子と一緒の依頼は、みにの分だけを宛先みにだけの新しい依頼IDで出し直し、元の依頼はほかの子の報告がそろったら状態の行を手で「完了」にする。理由が「同じ中身の依頼がほかにある」なら、そのままでよい |
| `mini-report-hold:<run>` | 完了報告が書けたか分からないまま30分たった・書けない状態が続いている | みにの完了報告ページに、その依頼IDの報告が載っていれば（遅れて書けた・手で書いた）、次の巡回から完了まで進む。載っていなければ、run の記録のみにの答えを見て、報告を手で書くか決める。りりは自動では書き直さない |
| `mini-announce:<run>` | 【受け渡し】を3回続けて出せていない、または【受け渡し】は出したが依頼の状態を「対応中」に3回続けて書けていない | みには動いているかもしれない（状態だけのときは動いている。報告はこのまま届く）。run の記録と依頼の状態の行を確かめる（りりは出し直し・書き直しを続ける） |
| `mini-version:…`・`mini-home:…` | Codex CLI・macOS の版、または専用ホームの設定が、確かめたものと違う | 起こさない。版を上げたときは、のあに頼む（上の「入れる」のとおり、初期化・境界の試験・本物の通しをやり直してから `MINI_VERIFIED_*` を直す）。専用ホームは配備の形に戻す |
| `mini-off:…` | 受け口が止まっていて、ほかの子と一緒の依頼のみにの分を起こしていない | 受け口を戻すと、待っていた分は次の巡回で進む |
| `mini-lane-failing:<回>` | みにの受け口が3回続けて途中で止まった（例：`state/mini` が書けない） | `state/mini` が読み書きできるか（持ち主・権限・空き容量）と `logs/patrol.log` を確かめる。直れば次の巡回から続きをする。また続けて止まれば、もう一度知らせる |
| `invalid:…`（みにの自動実行を保留） | みにだけの依頼を受付で保留した | 知らせの案内どおり。ふつうは書き直せば次の巡回で確かめる。run の記録を読めない・書けないときは `state/mini` を直すだけでよい（依頼は書き直さない）。続きの依頼は、まだ自動では起こさないので手で渡す |
| `mini-part-held:…` | ほかの子と一緒の依頼の、みにの分を受付で保留した（ほかの子には届けている） | この依頼はもう受け口に入らないので、みにの分だけを宛先みにだけの新しい依頼IDで出し直し、元の依頼はほかの子の報告がそろったら状態の行を手で「完了」にする（続きの依頼は手で渡す。みにの完了報告が出れば完了まで進む） |

会話が始まる前に終わった run（node や Codex が見つからない・専用ホームの config.toml を Codex が読めないなどで、会話が始まる前に終わった・起動そのものに失敗した）は、知らせではなく、みにの完了報告「できなかった」で届く。【受け渡し】と「対応中」は出さない（会話が始まってから出す決まり）。だから、みにだけの依頼は「未着手」のまま残るが、りりはその依頼をもう起こさない（みにの受け口がこの依頼のブロックで起こした run の報告なので、「同じIDの過去報告」とは見なさない）。報告の「次にやること」のとおり、`state/mini/stdout/<run>.stderr`（Codex のエラー）と `state/mini/logs` で原因を確かめて直してから、新しい依頼IDで出し直す（元の依頼はそのままでよい）。ほかの子と一緒の依頼は、みにの分だけを宛先みにだけの新しい依頼IDで出し直し、元の依頼はほかの子の報告がそろったら状態の行を手で「完了」にする。ログイン切れはこれに当たらない（Codex は会話を始めてから 401 で失敗するので、ふつうの「できなかった」で、理由に「ログイン切れか認証の誤り」が出る）。

## Notionの同時編集への備え

書き込み前のlast_edited_timeと本文を記録し、更新直前に再読込、更新直後にも再読込して比較します。本文や編集版の競合、更新結果や後の読み取りが不明な場合はheldにし、自動で上書き修復・次の処理へ継続しません。

前後本文は `logs/notion-audit.jsonl` へ伏字付き・所有者だけが読める権限で保存します。これは復旧判断用で、Slack・Notion・GitHubへ送信しません。本文には私的な情報が含まれ得るのでローカルで保護してください。

Notion APIには条件付き更新（CAS）がないため、直前の読取とPATCHのすき間に行われた編集をこちらが上書きする競合は、完全には防止・検知できません。編集時刻だけでは同じ分の中の編集を区別できない場合もあります。本文の比較は継続します。

**依頼の本文を直す前に、まずSTOPを置いてください。** その時点ですでに動いている見回りが終了し、進行中の通信も終わったことを、プロセスや動作ログで確認してから編集します。STOPを置くだけで送信済みの通信が取り消されるわけではありません。編集・保留の確認が終わってからSTOPを外します。この手順を配備前に運用へ組み込んでください。

## ログの内容とアカウント違い

9列表の3列目は何を拾ったか・どこで止まったか、6列目は実際にした操作です。投稿は「依頼ID を投稿した」／「#りりの指示部屋に投稿」、報告は「報告者の完了報告から 依頼ID を拾った」／「たかむねりりあいすに報告」とします。取消した転送は「未送信」と明記し、報告済みと表示しません。Slackの証拠は実際のtsから計算した `YYYY-MM-DD HH:MM JST ts …`。履歴から後で確認した場合も、確認時刻を投稿時刻として使いません。練習・手動確認では存在を確認していないtsを作りません。「完了にした」には依頼ページのURLを残します。過去ログは書き換えません。

アカウント違い・EXPECTED_SLACK_*未設定の停止は60分に1件まで出来事を保持します。不一致中も、別認証のNotionへ3時間ごとにログだけを同期します。依頼・報告の読み取り、状態更新、Slack投稿はしません。練習ではログ表の読み直しと検証まで行い、書き込みは止めます。STOPや時間切れ、Notionの障害・結果不明があれば記録を保持して保留します。設定ファイル自体の構文不良・破損などで設定を読めない場合は、この同期もできずローカルの停止記録だけです。

ログ表は発見時の全行を重複照合に再利用し、書き込み直前の再読込は維持します。1バッチの通常経路は全行読み取り2回で、3回目の重複読込を除きました。ページ分割・複数バッチ・復旧確認時には追加読み取りが必要です。

### events.jsonlが壊れたとき

自動で壊れた行を捨てたり、初期化したりしません。まずSTOPを置き、動作中の見回りと通信が終わるのを確認してください。本人がevents.jsonlと状態ファイルを**原本のまま別名で保全**し、壊れた行の出来事IDをバックアップ・状態のlog_buffer・Notionの表と照合して、内容を確認できた行だけを正しいJSONに修復します。原本は消しません。内容を確定できなければ停止を続け、うさへ確認してください。状態ファイルを削除しての再開、行を飛ばしての継続は禁止です。修復後も練習で確認し、本人の判断でSTOPを外します。

## ログの容量通知

7日／30日の年齢判定は使いません。logsとstateの通常ファイルの合計が既定50 MiB（52,428,800バイト）を超えたら、3時間ごとのまとめ報告で整理するか聞きます。前回の通知成功から7日以上空け、未送信・保留の同じ通知は重ねません。1回4件の投稿上限に数えます。

閾値は.envの `LOG_SIZE_NOTICE_BYTES` で指定できます。ログ・状態・練習記録・監査ログを自動削除する処理はありません。本人が確認して整理します。

## 異常時の停止

Python 3.11より古いと、通常処理の読込前に固定の画面通知を試みて終了します。LLM呼出中のSTOPや実行期限も握りつぶさず上へ伝え、STOPならその回を終了します。通常の通信障害だけは固定文面へ切り替えます。想定外エラーも最後で受け止め、秘密を伏せたローカル記録と固定の画面通知を行います。通知はmacOSのosascriptを使い、この環境では実機表示は未確認です。画面通知に例外本文や秘密は入れません。

## 未検証・配備しない範囲

本人からv1.0.2の本番ログ障害報告を受けていますが、このv1.0.3修正版の実機読取・投稿・Notion書込、Noa実起動、Hermes推論、画面通知・5分運転は開発側では未検証です。模擬試験合格は本番実行やNoa ONの承認ではありません。

本体はLLM OFF・Noa OFFで先に更新・確認します。Noaはレビュー後、既存設定・利用条件を確認して本人の別のOKを得てから [有効化手順](noa-activation-v1.md) へ進みます。実API（Slack・Notion・Noa URL）の呼出し、Mac配置、launchd操作、実際のNoa ONは今回行っていません。

- Bearer 認証、`anthropic-beta: experimental-cc-routine-2026-04-01`、`anthropic-version: 2023-06-01`、JSON `{ "text": ... }` を用います。本文に送信者 ID、JST 送信時刻、元メッセージ、Slack の検証済み permalink を入れます。確認済みの本人ID `U0C5V11S37X` は「たかむね（ID）」と表示し、未知のIDには名前を推測して付けません。元本文は状態・出来事・練習ログに保存せず、未実行分は次回に Slack から再取得します。待機中に本文・送信者が変更されたものは実行しません。
- 承認済み指示チャンネル `C0CFM2HRA5V` の文字列 `@のあ` または `＠のあ` を含む新規の通常ユーザーメッセージだけ対象です。照合だけを揃え、元本文を変更して転送しません。りり `U0CFH9JRCKV`・設定された自分自身・`bot_id` / `subtype` / `bot_profile` を持つ投稿は除外します。スレッド返信は `conversations.history` で取得される範囲のみで、スレッド全件巡回はしません。受付依頼は新しいメッセージとして投稿してください。
- モードごとの初回有効実行時刻を cutoff として保存し、過去の投稿は実行しません。OFF を観測した実行でローカルに境界を保存し、未送信のqueued/retryは起動せず終了した記録として残します。再ON時は境界をその時点へ更新するため、OFF期間の投稿をまとめて起動しません。OFF 中はNoa用Slack読取・通知・API呼出を行いません。送信中・結果不明・成功済みの記録、重複防止、送信回数は削除しません。Slack 履歴を全ページ読み終えるまで watermark と待機項目は変更しません。チャンネル＋文字列の完全な ts で恒久重複防止します。
- Noaの履歴・リンク取得や設定等の通常障害は、依頼・完了報告の処理から切り離します。安全な固定文面で一度だけ知らせ、通常の依頼処理を進めます。STOP・実行期限・アカウント違いは握りつぶさず、その回を停止します。Noa通知自身の照合・送信障害も、通常の依頼を繰り返し妨げないよう分離します。
- 通知は「結果不明」「明示的な拒否」「変更・削除や認証情報混入による未送信」を区別します。既に取得・検証済みのSlackリンクがあれば確認先として付け、未取得のリンクを作りません。認証・設定など同じ原因はまとめ、1回成功しただけでは再通知を許可しません。1時間にわたって正常な処理を継続できた場合だけ、次に同じ原因が発生したときの通知を再び許可します。15分超の空白・OFF・途中の失敗は継続成功に数えません。認証・設定は成功したfire応答が証拠で、空の履歴読取だけでは復旧扱いにしません。ログのメモも日本語です。APIのURL・トークン・元本文は保存せず、安全確認済みのSlackリンクとsession URLだけを必要な証拠として扱います。
- STOP中やMac停止中にOFFを観測できなくても、Noa処理の前回記録から15分を超えて空いたときは、新たにONにしたのと同じ境界を作ります。時計が後退した場合や旧状態に時刻記録がない場合も安全側に区切り直します。古いqueued/retryや空白期間の投稿は起動せず、完全な履歴読取後に「起こさなかった @のあ が◯件あります」と一度だけ知らせます。削除済みなど履歴にない未観測投稿は数えられません。途中読取失敗では件数を推測せず、次回確認します。新しい指示の受付を古い集計より先に処理します。
- 15分以内にOFF→ONを戻し、その間にOFFを観測する実行が一度もなかった場合は、その変更は検出できません。STOP中に状態を変更しない原則は維持しています。実際のOFFを観測した場合は空白の長さによらず境界を更新します。
- 実送信は1見回り1回・直近1時間10回まで。429 とその再試行も回数に含み、上限超過は保留待ちにします。STOP 時は送信せず、練習時は実行なしの記録だけです。
- 送信直前に sending を fsync 保存します。429 の明確な拒否だけ `Retry-After` 後の別見回りで1回再試行します。タイムアウト、接続断、5xx、不正な応答、送信途中のクラッシュは HOLD にし、自動再送しません。その他の明確な拒否は終了します。最終失敗・HOLD の通知は同じ outbox キーで一度だけ予約し、通知自体の結果不明も既存の再送防止に従います。通知の exactly-once 配達を保証するものではありません。
- 成功には `type: routine_fire`、`claude_code_session_id`、それと一致する `https://claude.ai/code/{id}` の `claude_code_session_url` が必要です。ログは進捗「@のあ のメッセージを拾った」、動作「のあを起こした」、証跡に検証済み session URL を記録します。練習・拒否・HOLD を成功扱いしません。

HOLD は利用者による session 履歴確認が必要です。`--status` の `held` に種類 `noa`、チャンネル・ts・理由・試行回数を安全に表示します。Slack と Claude Code の session 履歴を本人が確認した後、`python3 patrol.py --resolve noa C0CFM2HRA5V:<正確なts> reviewed` でローカルの確認済みにできます。このコマンドは通信せず監査記録を残すだけで、起動成功・キャンセルを主張せず、再試行を許可せず、重複防止・試行回数も保持します。未送信の Noa 通知だけ取り消し、結果不明の通知は別の通知保留として残します。この版は Noa の HOLD を再試行へ戻す CLI を提供しません。状態ファイルを削除して再実行しないでください。未実行本文が Slack から取得不能になった場合も、自動で内容を推測・再構成しません。
