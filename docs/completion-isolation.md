# 完了判定の確認待ちを依頼ごとに分離する v1.4.3

2026-11-18の本人依頼「改善して動かして。全てが止まってる」に基づく。URL任意化後に表面化した、1件の原本不一致で以降の完了判定・保守・ログ同期・巡回完了記録まで到達しなくなる問題を修正する。

## 処理と安全条件

完了報告が揃った依頼について、現在の原本がない／配信時と本文・ブロックが違う／元の状態を一意に確認できない場合は、その依頼の `completion_hold` に理由と観測時刻を記録して次の依頼へ進む。指示は既に配送済みなのでrequest.statusはpostedを保持し、instructionのheldや再配送に取り替えない。原本・受付snapshot・送信済み本文・marker・ts・receiptを変更しない。

理由はsource_missing／source_changed／source_status_changed。1回の確認待ちにつき固定keyの通知を永続化し、再巡回で重複通知を作らない。投稿枠がなければqueuedのまま次回へ回る。sending／heldの結果不明は従来の照合条件を維持する。

同じ受け付け済みブロックと本文に戻り、状態も許可範囲に戻れば確認待ちをresolvedにする。その後も最新の結果・宛先全員・原本一致を確かめてから完了する。古い完了報告で新しい一部完了／できなかったを上書きしない。既に送った指示や報告の再送はしない。取り消すのはまだ送っていない確認通知だけ。

隔離するのは書込前に判定できた原本の3条件だけ。壊れた受付snapshot、STOP、期限、アカウント不一致、通信障害、Notion更新の競合・結果不明は従来の停止条件を維持する。実書込の失敗を「原本変更」として成功扱いにしない。

## 状態と復旧の表示

`--status`のcompletion_reviewsに安全な依頼ID・理由・最初／最後の観測時刻・原本復元が必要なことを表示する。本文や依頼元の説明文は表示しない。任意化した作業場所URLを再び完了条件にしない。

確認待ちがある依頼だけは未完了のまま残るが、巡回は保守・ログ同期・last_run_at更新・後続の通常処理まで進む。全体の実行が成功した場合はstatus=okにcompletion_reviews件数を添え、正常巡回と個別確認待ちを区別する。ほかの従来heldがあれば既存のheld表示を維持する。

未解決のcompletionレビューがある間は一般の「直りました」通知を抑止する。以前のlast_errorが履歴に残っても、完走時刻・新しいerror serial・個別のレビューを合わせて判断する。過去のエラーや保留を手動で消さない。

## 適用と検証

実Patrolの架空2依頼で、先頭の原本変更により後続の正常依頼がdoneにならない失敗を先に再現した。変更・欠落・ブロック差替え・状態変更を分離し、後続依頼の完了・ログ同期・last_run更新と、指示再送なしを検証する。STOP・期限・競合は伝播することも確認する。

Mac適用では専用STOP・自然終了・最新state/logsと既存設定の保全後にコードだけを反映し、同じ300秒巡回へ戻す。手動の試験投稿・AI起動・原本やsnapshotの修正は追加しない。実際の完了増分、ログ同期、残る確認待ちと通常周期の完走は別に読戻して記録する。

通信禁止の最終回帰は全1099件成功（既存1083＋新規16、失敗・error・skip 0）。Python119本のAST・空白検査も成功。新規16件では原本3条件・現在状態行の欠落と不正・受付snapshot破損・書込時STOP／期限／競合・最新結果の優先・低投稿上限と通知1回・statusの安全な表示・一般復旧通知の抑止を確認した。Standards／Specの独立レビューの未解決必須指摘は0。実際のMacの正常周期と残件数は配備後の記録で別に確認する。
